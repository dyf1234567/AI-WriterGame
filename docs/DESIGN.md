# 《双界录》游戏设计定稿

> 本文件保留历次设计讨论。当前机制以 [RULES.md](RULES.md) 为准；2026-10-18 已修正短付交易、首次加载、归档切换及信息公开边界，不再沿用本文件中的旧实现描述。

> AI 主持的都市修仙双穿互动小说——一个你不在线也在自己转的小世界。
> 标 ✅ 的为用户明确确认项；标 ⚙️ 的为默认建议值，用户未反对，后续可改。

## 一、核心玩法

- AI 实时生成剧情，每段给出 3~4 个选项，同时提供自由输入框 ✅
- 玩家做选择推进剧情；大主线（两界之谜 / 渡劫飞升）节奏自由，可自由探索触发支线 ✅
- 关系是活的：双层关系网（玩家↔NPC、NPC↔NPC 自主发展恩怨情仇）✅
- 离线演化：不玩的时候世界也在走，回来时结算 ✅

## 二、世界观 ✅

- **都市侧**：现代都市，主角是普通高中生，暗地里另有隐秘
- **修仙侧**：可穿越的修仙世界，宗门、境界、恩怨
- **穿越规则** ⚙️：系统解锁后随时可穿，重大剧情节点可临时锁定
- **时间流速** ⚙️：都市侧与现实 1:1；修仙界加速——现实 1 小时＝修仙界 1 天

## 三、主角与系统

- 主角：获得"系统"的普通高中生 ✅
- 系统面板：境界、修为进度、属性 ⚙️
- 任务：主线任务＋自由探索触发的支线任务 ⚙️
- 每日签到：灵石 / 功法残页 / 修为灌顶等奖励 ⚙️
- 境界体系 ⚙️：凡人 → 炼气 → 筑基 → 金丹 → 元婴 → 化神 → 渡劫 → 飞升

## 五、离线演化机制（真实实现方式）

本地程序无云端常驻。实际做法：**下次打开游戏时按离开的真实时长结算**——
都市侧按 1:1 折算经过的天数，修仙侧按 1 小时＝1 天折算；由 AI 批量生成
"你不在时发生了什么"事件流 + NPC 留言，写入收件箱，并结算关系变化。
为控制 token 成本，采用批量摘要而非逐 NPC 逐时辰模拟。

## 六、界面（用户三次修正后定稿 ✅）

**三栏分格布局 ＋ 阅读式剧情流 ＋ 点击式多风格切换 ＋ 地图系统。**

- 顶栏：游戏名 / 当前世界与位置 / 穿越按钮 / **风格色点一键切换**（点击即换，含夜间模式：深夜 · 墨纸，另有羊皮卷 · 青岚，选择被记忆）/ 好感度显隐开关 / 新游戏
- 左栏分格：**地图**（当前位置、都市/修仙界两界地点切换、点击地点即前往/穿越前往、未探明地点显示？？？）、修行面板（境界、修为进度、属性）、每日签到、任务（主线+支线）、背包
- 中栏分格：阅读式剧情流（衬线排版），选项按钮组＋自由输入框
- 右栏分格：关系网（NPC 卡片＋NPC 彼此恩怨）、收件箱（离线事件与 NPC 留言）
- 语音朗读：预留位置，第一版不做 ✅（用户"还没想好"）

## 六A、地图系统 ✅（用户追加并修正为可视化）

- **可视化 SVG 地图**：不是列表，而是画出来的地图——都市侧暂以"世界地图"占位（地名全部虚构：青临市、东澜自由港、北漠雪原、西岭古国、沧溟群岛），修仙侧暂定现有布局（太虚宗山门/弟子居/坊市＋两处迷雾）
- **已探明地点正常显示**（地名标记，点击即前往；异界地点＝穿越并前往）；**未探明压黑**（黑色迷雾遮盖，不可点击）
- **点击查看界面 ✅（用户追加）**：点击小地图打开大图查看窗（两界切换、大尺寸地图）；点击地点标记先展示详情卡（名称/描述/所在世界/是否当前所在），确认后才前往——避免小地图误触直达
- 当前位置有脉冲标记；地点带坐标（百分比），剧情 AI 新登记的地点无坐标时按名称散列自动落位
- 引擎契约：`location`（剧情落脚点变化）与 `new_places`（新地点登记/揭示），由剧情 AI 在场景转移与探索时输出；揭示既有迷雾地点或登记全新地点
- **世界规模**（用户要求"像正儿八经的游戏"）：都市 8 地（城市/荒野/秘境/海域），修仙 10 地（宗门/城镇/荒野/秘境），各有类型标签与两句话描述；NPC 有"常在地"，详情卡显示常在此地之人
- **快捷动作**：输入框上方提供 修炼 / 探索此地 / 查看四周 三个快捷键，探索可揭示迷雾地点

## 六B、自由度原则 ✅（用户追加）

提示词中明确要求模型：两个世界可自由探索，玩家任何合理行动都给有内容的回应；世界不围着玩家转（NPC 有自己的日程动机，npc_events 体现世界呼吸）；未明说的场景元素（小店、摊贩、路人）按世界观自行补全；适度主动制造偶遇与意外；修炼按环境灵气给收益（都市低、修仙高）。

## 七、技术形态 ✅

- 后端：FastAPI（本地服务），前端：原生 HTML/CSS/JS 多分格面板
- 模型：国内 OpenAI 兼容接口（.env 配置 base_url / key / model）

### 八A、人物名册、身份与初始功法

- **登场即登记**：剧情中任何有名字、且可能再次出现的人物，由模型经 `new_npc` 登记进名册，与预设主角团同构（人设/常在地/好感/关系标签/记忆）。未登记的人物下一回合即从世界上消失，因此提示词明确要求"给了名字就必须登记"；无名背景群众不登记。
- **去重与上限**：按姓名匹配去重，已有角色不会被重复登记。名册上限 `MAX_NPCS = 30`，超限时按"最久未登场"淘汰剧情生成的人物，预设主角团永不淘汰。
- **登场回合**：`last_seen_turn` 在登记、好感变化、关系事件时刷新；提示词中的名册按相关度（当前所在地 ＞ 近期登场 ＞ 主角团）排序并截断至 16 人，截断处附说明，避免模型误判未列出者已消失。
- **身份落档**：主角的社会身份（入门、拜师、晋升、被逐、头衔）按世界分别存于 `player.identity`，由 `identity_update` 更新，进入每回合提示词与左栏修行面板。都市侧默认「临江三中·高三学生」。
- **结算顺序**：位置 → 新人物登记 → 好感 → NPC 间事件 → 身份，保证同回合的关系变化能落到刚登场的人物身上。
- 模型产出的所有登记字符串统一剥离尖括号后入库（前端按 innerHTML 渲染关系网与人物详情）。
- **初始功法一次性闸**：`player.technique` 记账（路线／功法名／品质／领取回合），由 `technique_grant` 申报。已录入后再次申报一律拒绝、功法不入背包，并在面板写明被拒的功法名。路线归一到设定集六条（剑／体／法／魔／丹／阵符修），对不上则原样保留；**品质由系统固定为「上品」**，模型自填的 grade 无效。发放成功后由引擎把功法作为物品放进背包（描述可沿用申报文本），因此提示词明确要求初始功法不走 `item_gained`。
- 日后再得的传承或改修功法属普通剧情物品，仍走 `item_gained`，不触碰 `player.technique`。
- 功法状态进入每回合提示词（未领取写"待领取"，已领取写"不得再发初始功法"），并显示在左栏修行面板。

### 八B、收支账本

叙事与账本必须对得上：剧情里花掉的钱要真的从背包里扣走，得到的东西要真的入账。

- **双向申报**：`item_gained`（带 `count`）与 `item_spent`（带 `count` 与 `reason`）构成完整收支。此前只有收入通道，模型写"你花三块灵石买消息"而账本不动。
- **收入护栏**（`config.py` 可调）：单回合灵石上限 `GAIN_CURRENCY_CAP = 30`、商城在售物品上限 `GAIN_CATALOG_CAP = 1` 件、其他物品种类上限 `GAIN_KIND_CAP = 3`。在售物品能半价卖出，因此是变现通道，必须收紧；非在售的剧情物品（残页、舆图、信物）不受行情约束，仍可自由获得，但卖不出钱。
- **系统专属物品**（`models.SYSTEM_ITEMS`，当前为「系统抽奖券」）：只能经系统通道增减——开局发放、抽奖时扣除。出现在 `item_gained` 或 `item_spent` 里即被拒绝、在面板写明，且不占用其他物品的种类额度。原因：抽奖券不在商城目录内，会落到"其他剧情物品"通道（单条数量上限 999），一次失守即可凭空造出上千次抽奖，再经奖池中的在售物品半价变现——比直接印灵石的量级更大。功法一类剧情物品**不入**此清单，仍由模型按规则发放。
- **内部通道不受限**：每日签到与支线奖励由引擎直接发放，不经护栏。
- **余额不足的处理**：单次调用架构下剧情先于结算写成，因此不改剧情，只按实有余额扣到零（账本永不为负），并在面板写明短付数额；下一回合的背包快照会让模型看到真实数字。
- **账目可见**：所得、支出、截断与短付都进 `system_notice`，玩家在面板上直接看到"所得：坊市舆图 +1／支出：下品灵石 -2（向摊主买下坊市舆图）"。
- **提示词侧约束**：状态快照显式给出"可用灵石"，并写明三条义务——花钱必须申报、所得必须申报且受护栏、余额是唯一事实不得与之矛盾。

### 八C、剧情压缩与归档

滚动摘要控制上下文长度，但**压缩失败不允许销毁正文**。

- **触发与窗口**：剧情超过 `COMPACT_THRESHOLD = 30` 段时压缩，成功后只保留最近 `COMPACT_KEEP = 12` 段；`MAX_STORY = 60` 是状态窗口的硬上限。
- **失败即保留**：模型调用失败、或返回空摘要，都按失败处理——不截断、不写假摘要、保留全部正文，并在面板告知玩家"已保留全部 N 段正文，5 回合后重试"。
- **重试冷却**：失败后 `compact_retry_at_turn` 推后 `COMPACT_RETRY_INTERVAL = 5` 回合，避免模型持续不可用时每回合空烧两次调用（每次含 1 秒退避与最长 120 秒超时）。
- **归档而非删除**：任何移出状态窗口的正文都先追加到 `data/story_archive.jsonl`（含回合号、所在界、正文、选项与玩家当时的选择），归档写失败就不截断。硬上限 `MAX_STORY` 走同一条路径，因此长期离线或模型故障期间正文也不会消失。
- 此前的实现是"压缩失败只 `pass`，随后无条件截断到 12 段"，一次失败即静默丢失 18 段正文且无备份。
