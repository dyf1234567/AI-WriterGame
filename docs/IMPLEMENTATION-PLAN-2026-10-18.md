# 双界录详细实施计划

日期：2026-10-18。

状态：待实施的工作计划。本轮仅编制计划，没有修改运行代码和正式存档。

依据：[重构方案](REBUILD-PROPOSAL-2026-10-18.md)、[现行规则](RULES.md)、当前 app / static / tests 目录。本文中的新机制为推荐设计，尚未替代现行定案。

## 1. 首个版本的交付目标

交付一个能反复游玩、约 30—50 次有效行动完成一章的单人叙事 RPG。范围为青临市的学校与家庭、白溪镇及周边，6—8 个核心 NPC、8—12 个可互动地点。自由行动和条件事件结合，玩家可以拒绝、失败、离开和返回。

保留：随时免费双穿、返回原落点、境界成长主干、初始功法与抽奖、不强制追查系统身世。保留上一轮完成的阅读、备份、版本检查和展示隔离修复。

首版完成的体验：

- 玩家知道自己在哪里、谁在场、近期有哪些事情，以及行动大约需要多长时间。
- 关键行动改变真实资源、人物立场或事件状态，后果在后续可以被看见。
- NPC 有自己的目标和不愿接受的条件，不因好感高就无条件服从。
- 同一件旧事在长局中可以被检索；秘密按获知过程传播。
- 一章至少有三种不同收束结果，其中包含拒绝或失败后仍可继续的路径。
- 模型不可用时，确定性行动与已确认进度仍可保留和读取。

暂放后续版本：完整九州模拟、大量职业和技能、多人联机、复杂自动经营、全员逐回合推理、全新前端框架、向量库与图数据库。早期战斗仅实现本章需要的少量动作和明确后果。

## 2. 总体顺序、依赖和工作量

工作量按一名熟悉项目的开发者同时负责内容整合估算，包含实现、内容接入、必要验证和修正。以下 34—50 个有效工作日仅为初步排期参考，阶段 1 和阶段 2 完成后重新估算；不等于模型持续运行时长或固定交付日期。外部试玩招募、反复创作和供应商故障等待可能延长日历时间。

| 阶段 | 主要结果 | 前置条件 | 初估工作日 |
|---|---|---|---:|
| 0 | 可恢复基线、隔离验证环境 | 无 | 1—2 |
| 1 | 世界规则、章节蓝图、数据与动作协议 | 0 | 3—4 |
| 2 | SQLite、新周目与分支、旧档导入 | 1 | 5—7 |
| 3 | 统一行动裁决、世界时钟、基本玩法闭环 | 2 | 5—7 |
| 4 | NPC 目标、知情范围和长期记忆 | 3 | 4—6 |
| 5 | 第一章事件、人物行动与有限世界演化 | 3、4 | 4—6 |
| 6 | AI 意图解析、对白和叙事接入 | 4、5 | 5—7 |
| 7 | 场景界面、人物与任务视图、恢复体验 | 6；界面结构可在 5 后开始 | 3—5 |
| 8 | 长局评测、真人试玩、发布与回退演练 | 7 | 4—6 |

关键依赖：规则与协议 → 存储与身份 → 行动与时钟 → 人物记忆 → 章节事件 → AI 演绎 → 完整试玩。

内容工作可以穿插进行：阶段 1 定章节骨架；阶段 2—4 完成人物卡和事件卡；阶段 5 接成可运行章节。不要等待所有技术模块结束才开始写剧情。

里程碑：

| 里程碑 | 达到时间 | 可直接审查的成果 |
|---|---|---|
| M0 设计可执行 | 阶段 1 结束 | 规则表、地方地图、人物卡、章节事件图、行动样例 |
| M1 规则版可玩 | 阶段 3 结束 | 无模型也能移动、交易、修炼、穿越、保存恢复 |
| M2 内容版可玩 | 阶段 6 结束 | AI 演绎完整一章，NPC 能重逢、记事、拒绝并承担后果 |
| M3 可交付试玩 | 阶段 8 结束 | 验收报告、迁移说明、发布包及回退方法 |

## 3. 阶段 0：保存可恢复的开发基线

### 任务

- P0-01：建立本地版本控制。当前项目没有 .git；运行存档、密钥、缓存和日志不进入源码版本管理。
- P0-02：登记当前 API、存档字段、功能入口与已知缺口，形成简短的功能清单。
- P0-03：为开发、演示、自动验证、人工试玩分别设置数据目录，沿用 SJL_DATA_DIR 的隔离能力。
- P0-04：保留正式存档及关联正文/NPC 归档的可恢复副本，记录文件完整性。备份不得进入公开仓库。
- P0-05：运行现有状态、回归、前端和接口检查，记录结果与测试条件；接口检查仅对隔离实例执行。
- P0-06：建立任务台账，记录每项的状态、依赖、改动文件、验证结果和剩余问题。

### 交付与验收

交付开发基线、隔离启动说明和初始验证报告。验收条件：演示与测试不会改动正式进度；能从备份打开原型；现有失败用例逐项有记录，不能把旧问题误记为新重构问题。

## 4. 阶段 1：将世界设定和故事目标写成可执行规则

### 任务

- P1-01：写一页产品说明，明确核心体验、首章范围、支持的自由度和阶段结束条件。
- P1-02：统一 RULES、WORLDSETTING、GAME-OVERVIEW、DESIGN 的职责。已定案、候选设定、历史讨论分别标记，消除同一地点或机制的冲突描述。
- P1-03：制作地方节点地图。每条路线记录起终点、耗时、可达条件、已知危险和控制势力；都市交通与玄灵界道路分开配置。
- P1-04：确定时钟、离线、生理年龄、携带和通信的推荐参数，写入规则决策表。
- P1-05：制作 6—8 张核心人物卡：目标、利益、底线、日程、关系、初始所知、可能误解、独特表达和变化条件。
- P1-06：绘制第一章事件图，规划约 12—18 张主干、人物与后续回收事件卡；每张都包含触发、拒绝、过期、解决与后果。
- P1-07：定义 Action、Outcome、Event、Knowledge、Commitment、SceneContext 等边界协议，字段使用实体 ID，不以姓名承担唯一身份。
- P1-08：写 20—30 个行动与预期后果样例，覆盖自由行动、拒绝、物品使用、旧事追问、穿越逃离与返回。

### 需要在本阶段落定的设计项

| 项目 | 推荐起点 | 定稿时必须说明 |
|---|---|---|
| 时间 | 共用基准时钟，都市 1 倍、玄灵界 24 倍；先换算行动耗时 | 在线行动与现实离线如何衔接、长行动如何中断 |
| 生理年龄 | 按主角亲身经历的时长累计 | 延寿、休息和疲劳的关系；旧档从何时开始计 |
| 离线 | 保留世界推进；超出单批处理量的时长进入待结算队列 | 哪些事件可离线结算，错过关键事件后如何继续 |
| 跨界携带 | 使用简单明确的容量与对象规则 | 活体、容器、储物袋、随身装备如何计量 |
| 通信 | 默认消息只在对应世界和有效通信条件下送达 | 手机、玉简和系统通知是否跨界以及依据 |
| 失败 | 允许错过、损失和关系破裂，保留继续游玩的路径 | 首章是否支持主角永久死亡、重大伤残及回退政策 |
| 战斗 | 只覆盖首章动作，使用明确属性、条件与随机结果 | 胜败、撤退、伤势、资源消耗和信息可见性 |

这些属于待设计参数，不阻止先做卡片和协议。实现前按现行规则和产品目标收敛；确实改变核心玩法且无法据现有授权判断的事项，再单独提出具体取舍。

### 交付与验收

交付规则决策表、地方地图、人物卡、事件图、数据协议及行动样例。用纸面或模板方式走完至少五条路径：主动帮助、交易解决、拒绝参与、行动失败、跨界离开后返回。每条路径都能指出状态变化与后续入口。

建议内容目录：content/worlds、content/characters、content/chapters/chapter_01、content/items、content/rules。小规模内容采用可校验的 YAML 或 JSON，阶段内选定一种主格式；不急于开发可视化编辑器。

## 5. 阶段 2：建立新存储、稳定身份与可回退迁移

### 任务

- P2-01：在现有 storage 外引入存储接口，使运行入口不再直接依赖 state.json 的具体结构。
- P2-02：建立 SQLite schema 与递增迁移版本，启用外键约束，定义数据库忙等待及失败反馈。
- P2-03：实现周目、读档分支、实体 ID 和别名。所有查询显式限定周目与分支，分支只继承分叉点之前的数据。
- P2-04：实现追加事件、当前状态、回合记录和快照的同事务提交。事件记录顺序、原因、规则版本、随机结果与参与对象。
- P2-05：实现待处理行动：action_id、请求内容摘要、基准版本、处理状态、候选结果、最终响应。相同 ID 不允许对应不同请求。
- P2-06：开发旧档只读导入器，先导入临时数据库，输出字段映射、数量核对和缺失信息报告。
- P2-07：实现数据库一致性备份、导出、恢复和新建分支。备份使用 SQLite 的一致性机制，不能在活跃写入时只复制主文件。
- P2-08：按整个周目选择旧引擎或新引擎，避免同一周目两个存储同时写入。第一轮试玩使用独立新档。

### 最小数据集合

| 集合 | 用途 |
|---|---|
| campaigns / branches | 周目与读档分支 |
| entities / aliases | 人物、地点、独特物品及别名 |
| actor_state / relations / inventory | 当前人物状态、关系和持有物 |
| events / turns / snapshots | 历史、完整回合和恢复点 |
| knowledge / commitments | 知情证据、承诺与未结事项 |
| story_instances / scheduled_actions | 当前剧情实例与到期行动 |
| content_versions / schema_migrations | 内容和数据库版本 |

### 迁移边界

旧档已知境界、物品、位置、成长目标和正文尽量保留。旧摘要作为历史摘要，旧知情记录只在有明确证据时导入，无法判断的标记为未知。不能根据后台人设推断主角已经知晓，也不能虚构旧事的准确日期和目击者。

新引擎生成的全部新状态未必能降级到旧格式。因此回退旧程序时恢复的是迁移前检查点，不承诺将新进度无损反向转换；新数据库仍保留，避免误删进度。

### 验收

导入前后核对物品数量、余额、境界、人物和正文条数；重复导入不复制数据；中断导入不损伤旧档；分支 A 的新增事件不会被 B 查询到；恢复快照后已确认状态一致。模型等待期间不占用长写事务。

## 6. 阶段 3：统一行动裁决与世界时钟

### 任务

- P3-01：新增行动服务，统一接收按钮指令与自由行动解析结果。数据结构包含操作者、动作类型、目标、参数、来源和基准版本。
- P3-02：将移动、穿越、买卖、使用、装备、炼丹、签到与抽奖逐步接入相同的事件提交入口；保留各自已经定案的独立规则。
- P3-03：为首章加入交谈、交付、承诺、等待、休息、修炼和简单冲突动作。其他复杂动作先返回明确能力边界，不能假称已经执行。
- P3-04：集中检查资源、位置、可达性、行动资格和对象状态。购买成功必须有商家与货物来源；人不在场不能直接当面对话。
- P3-05：实现结果对象：成功、部分成功、合理拒绝、需澄清、技术失败。合理拒绝是否耗时由动作规则决定；技术故障不冒充游戏后果。
- P3-06：实现两界日历、行动耗时与主角经历时间。计算优先使用整数或精确单位，避免反复换算丢失小数。
- P3-07：实现到期队列与分段长行动。长时间修炼或旅行分段推进，遇到定义好的中断条件时停在准确时间点。
- P3-08：实现首章需要的伤势、休息、修行与突破条件。十级成长主干保留，先细化本章使用的机制，未细化部分明确标记。
- P3-09：用模板正文跑通完整回合，使规则运行可脱离真实模型单独验证。

### 时钟的实现要求

模拟时间、现实最后同步时间、主角经历时间分别保存。模型响应等待不直接变成游戏耗时；明确结算过的离线区间不能再次结算。穿越瞬间本身不耗时，也不恢复伤势或资源。

离线批处理记录处理游标和剩余区间；同一时间段的补货、计划和任务到期只能执行一次。离线任务失败时保留未结算区间，不能直接更新同步时间并吞掉它。

### 验收与 M1

玩家无需接模型即可完成：进入城镇 → 购买物品 → 修炼或休息 → 建立一个有期限的约定 → 穿越 → 返回原落点 → 查看时间与资源变化 → 保存 → 重启恢复。

覆盖余额不足、库存不足、同名对象、过期任务、长行动中断、重复提交、版本冲突和穿越撤退。所有后果能找到对应事件。接口仍可提供兼容的公开状态视图，避免后端重构时整套页面同时失效。

## 7. 阶段 4：人物目标、知识边界与长期记忆

### 任务

- P4-01：将人物稳定人设与动态状态分开；增加目标、计划、底线、位置、日程和资源。
- P4-02：建立关系变化原因，首章先使用信任、亲近、戒备和人情债；数值范围和可变条件明确配置，不全部暴露给玩家。
- P4-03：定义每条知识的拥有者、内容、客观/传闻/推断类型、来源事件、获知时间及被更正或失效状态。信心程度仅是辅助信息，不作为真实性保证。
- P4-04：目击、交谈转述、书信和调查分别产生获知事件。不能将一批事件的见证者简单合并后共享全部内容。
- P4-05：承诺独立保存，使用 ID 和条件判断兑现、违约、撤销、过期；旧事实仍保留历史记录。
- P4-06：实现实体别名与基于场景的指代解析。“他”存在多个候选时返回歧义，不随意指定对象。
- P4-07：实现上下文检索：先限制周目、分支、人物及可见范围，再按场景、目标、未结事项、相关性和时间排序。
- P4-08：为每个检索片段保留事件编号，提供内部检索说明。摘要与索引可以重建，不删除权威事件以腾出提示词空间。
- P4-09：编制初始连续性检查集，优先覆盖过去实现最容易出错的场景。

### 必测场景

| 场景 | 期望行为 |
|---|---|
| 私下透露秘密 | 不在场且未获转述的人物无法检索秘密 |
| 甲转述假消息给乙 | 乙持有该信念，世界事实不随之改变 |
| 后来证实消息为假 | 旧消息可追溯，乙的当前认知被更正 |
| 50 回合后说“上次答应的事” | 能结合当前对象和未结承诺找到来源 |
| 治好伤势后重逢 | 记得曾经受伤，当前状态保持已恢复 |
| 读档走另一条路线 | 新路线不获得废弃分支中的消息 |
| 同名人物再次出现 | 依稳定 ID 区分，不自动合并档案 |
| 高好感人物收到过分要求 | 根据目标和底线作出有依据的拒绝 |

### 验收

数据查询层的秘密隔离和分支隔离用确定性检查验证；生成对白的隐性泄密另行评测。每个关键回忆能回查来源。未结承诺不因窗口变满被删除。先完成结构化与全文检索，再根据漏检样例判断是否需要语义检索。

## 8. 阶段 5：第一章事件调度与有限世界演化

### 任务

- P5-01：实现事件卡校验与加载，防止引用不存在的人物、物品或地点。
- P5-02：实现事件实例状态：未激活、可触发、进行中、解决、失败、过期、取消；状态转换明确合法条件。
- P5-03：实现触发优先级、互斥、冷却、重复限制和截止时间；每次场景只挑选有限事件，避免堆叠大量冲突。
- P5-04：实现规则化 NPC 计划：到期交付、出行、求助、拒绝、换班、补货等；只有条件满足才执行。
- P5-05：完成第一章全部事件卡与人物后续反应。三种以上收束需要改变世界状态、关系或后续可选路径，不能只换一句结尾。
- P5-06：让都市安排与玄灵界事件通过真实耗时相互影响；穿越后另一界不会自动暂停。
- P5-07：加入有限库存、补货和消息传播。背景只更新相关节点，远方九州保持传闻与配置留白。
- P5-08：添加可替代的线索和重新进入事件的机会，避免漏看一句话就永久卡住整章。

### 章节内容要求

首章至少包含：一个地方主要冲突、两条人物事件、一件都市侧需要履行的安排、一次有后果的拒绝、一次失败后的替代路径、两处可以事后回收的旧事。

“药材供应中断”可作为样例；正式制作时先检查与既有人物和存档的兼容性，再定稿。旧人物优先深化，避免为了凑数量随意替换已经建立的角色。

### 验收

固定行动序列能走完帮助、交易、拒绝、失败与离开再返回等路径。同一事件不会重复发奖，不会在结束后又当作未开始；人物知道事件结果必须有传递依据。玩家无须立刻拜宗门或追查系统身世，也能经历完整章节。

## 9. 阶段 6：接入 AI 演绎与自由行动

### 任务

- P6-01：按钮动作直接调用规则；自由输入先解析意图、对象和参数。玩家声称“我已经有一万灵石”不能直接写成余额。
- P6-02：将新人物、新地点、新道具或新传闻作为候选内容生成，经过命名、区域、能力和身份检查后才进入已确认世界。
- P6-03：按叙事和人物分别建立上下文。人物回应只获得该人物可知的信息；全知主持资料不能直接放进所有人物对话上下文。
- P6-04：叙事服务只接收经过裁决的结果、允许展开的细节和场景边界，不再向模型开放任意 state_updates。
- P6-05：建立正文输出结构：场景文本、建议行动、已公开信息引用；任何新增重要事实仍需通过明确候选入口。
- P6-06：校验地点、参与人物、资源结果和公开信息引用。文本中的暗示、口吻和遗漏，用场景评测与人工审读发现，不能仅靠字段校验宣称解决。
- P6-07：实现超时、限流、格式异常、重试预算与模板降级；同一候选结果重写正文时不重新抽奖或执行动作。
- P6-08：实现待处理回合恢复。提交前崩溃可继续处理，提交后丢响应可返回同一结果；版本冲突时丢弃旧候选，不静默套用过期结果。
- P6-09：记录模型、提示词版本、耗时、调用数、token 用量、费用可用性与失败类型。日志不保存 API 密钥，诊断导出限制敏感内容。

### 调用策略

普通确定性行动最多需要一次叙事调用；复杂自由行动允许增加一次解析。摘要按场景变化触发，NPC 计划优先规则执行。首版不要求多个模型角色每回合互相讨论；只有测得收益后再增加调用步骤。

模型等待期间不保持数据库写锁。前端可以显示处理状态，已经提交的历史正文可以继续阅读；未经确认的成功、奖励、死亡等重要后果不提前当作正式结果展示。

### 验收与 M2

使用固定样例与真实模型分别验证。未通过裁决的行动不能获得奖励；AI 描写与最终状态的差异有可复现样例；中途故障不会重复结算。玩家能在完整一章中观察到人物记事、误解、拒绝、重逢与事件回收。

## 10. 阶段 7：让界面解释场景、时间与后果

### 任务

- P7-01：剧情区展示当前地点、世界日期、在场人物和正在处理的行动；保留移动端阅读优先布局。
- P7-02：行动前提供可确定的基本成本提示，如旅行或等待时长；未知结果保持未知，不提前泄露剧情。
- P7-03：任务区区分成长目标、章节事件、个人承诺，展示已知期限与最新进展。
- P7-04：人物卡区分主角已知信息、共同经历和可见关系表现；后台目标与秘密不直接公开。
- P7-05：回合结果展示有依据的耗时、资源和事件变化，并能跳转到对应历史记录。
- P7-06：提供历史筛选、承诺追踪和“这条消息从哪里得知”的公开证据入口。
- P7-07：为重试、处理中恢复、存档迁移、备份恢复和分支切换提供清楚反馈。重复点击不建立重复行动。
- P7-08：保留键盘操作、文字即时显示设置、长文本滚动位置和小屏布局，检查字数较多时的实际阅读体验。

### 验收

首次试玩者能在开始几次行动内辨认位置、可行动对象、当前事项和穿越方式；桌面与常见手机宽度下可以完成整条章节路径；查看背包、任务或人物后能返回原阅读位置。

界面不显示实现术语、内部检索分数或待处理数据库状态。诊断信息单独放在开发视图。

## 11. 阶段 8：长局验证、试玩与交付

### 自动验证

- 数据与规则：保留现有有效用例，对新引擎补充事件提交、时钟、读档分支、迁移和重复请求的检查。
- 长局连续性：制作 100—200 次行动的固定情境，穿插旧事追问、秘密转述、承诺兑现、人物重逢和状态更新。
- 中断恢复：在候选生成、正文生成、事务提交前后模拟故障，检查进度与结果是否一致。
- 内容可达：逐条验证事件引用、前置条件、互斥关系、结束条件与拒绝后的入口。
- 真实模型：对代表性场景记录输出、错误、耗时和用量；不要只用演示输出证明 AI 体验通过。

### 真人试玩

建议第一轮 3—5 名不了解实现的试玩者，每人至少经历一个章节收束。记录完成路径、卡住位置、误解的规则、重复文本、人物失忆或泄密、选择是否改变后续，以及愿不愿意开第二局。

体验问卷每项使用 1—5 分，并保留具体例子：行动后果是否清楚、人物是否有独立诉求、旧事是否被记住、文本是否重复、是否能理解时间与期限。首轮先收集基线再确定改进目标，不用单一平均分掩盖关键问题。

### 发布门槛

| 项目 | 门槛 |
|---|---|
| 存档安全 | 无已知的丢档、串档、重复扣款或重复领奖问题 |
| 规则与知情查询 | 固定验收集全部通过；不以“总体通过率高”接受隔离失败 |
| 章节完整性 | 至少三种实质不同的收束；拒绝和失败均可继续 |
| 长局连续性 | 每个失败样例有结论；重复性错误修复后复测相关路径 |
| 实际体验 | 首轮试玩暴露的阻断问题已解决，并经过复玩确认 |
| 性能与费用 | 有指定模型下的中位耗时、P95、调用数和费用记录；目标在拿到基线后确定 |
| 恢复能力 | 完成数据库备份恢复、迁移前检查点恢复和版本回退演练 |

### 交付物

可运行版本、配置样例、首章内容包、旧档导入与限制说明、验证结果、已知问题清单、回退说明和下一版候选列表。源码、内容与数据库版本对应记录，避免更新内容后旧档无法解释事件。

## 14. 风险、降级与变更管理

| 风险 | 提前应对 | 仍未解决时的处理 |
|---|---|---|
| 内容越写越大 | 首章固定范围，新增需求进入后续列表 | 减少地点和支线，保住完整因果与结局 |
| 自由输入覆盖不了 | 分动作支持范围，保留需澄清与合理拒绝 | 关键流程提供可执行建议动作，不伪造执行成功 |
| AI 正文与结果不一致 | 权威结果结构化、有限上下文、保存失败样例 | 有限重写后使用准确的模板叙述 |
| 知识被摘要串给其他人物 | 知识逐项归属，检索先过滤后排序 | 停用有问题的摘要注入，回到来源事件 |
| 旧档历史不完整 | 原件保留、未知字段显式标记 | 旧档继续原型游玩，新引擎从新周目验证 |
| 模型耗时与费用上升 | 调用分类统计，规则更新不调用模型 | 减少非必要推理与后台摘要，保留主要叙事 |
| 离线跨过大量剧情 | 分批结算、明确期限、准备失败后入口 | 保留待结算区间和可解释摘要，不吞时长 |

每阶段只在交付与验收满足后进入下一阶段。阶段结束更新台账与估算，记录新增范围。代码调整和内容调整分别标明版本，已确认世界事实不能因换模型被静默重写。

## 15. 最先执行的一批工作

1. 建立源码版本与正式存档恢复点。
2. 在隔离目录重跑当前验证，记录基线。
3. 整理一页产品目标和首章范围。
4. 制作世界规则决策表，标出保留规则与待定参数。
5. 绘制地方节点地图及旅行时间。
6. 深化现有人物，完成第一批人物卡。
7. 制作第一章事件图及五条纸面路径。
8. 定义动作、结果、事件和知识协议。
9. 实现最小 SQLite 周目、实体、事件与回合提交。
10. 用“移动—购买—穿越—返回—重启恢复”做第一个可运行闭环。

这批工作完成后即能检查设计是否落得下去，再扩展到人物记忆与完整章节。实际进度以工作产物和验收结果记录，不将计划中的能力标记为已实现。
